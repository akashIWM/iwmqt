02 — Naye Files: Strategy Feed System

Yeh 5 files ek saath kaam karti hain

Yeh aapke senior ke ask ka jawab hai - "outside algo/strategist systems se connect karo, unka data dikhao, aur unhe command bhi bhej sako." Isko banane ke liye 5 files chahiye hui - 3 Python side par, 2 Node backend side par, plus frontend mein 1 hook.

strategy-feed/server.pyNaya

Kya hai

Python mein likha ek TCP server - yeh literally woh cheez hai jo senior ne ask ki thi.

Kyun banaya

Bahar ke algo/strategist systems ko ek jagah chahiye thi jahan woh apna live signal bhej sakein, aur jahan se unhe command (Deploy/Stop) mil sake.

Steps jo follow kiye

  • asyncio use kiya - ek saath multiple systems connect ho sakein, ek ke wait mein doosra na ruke
  • Protocol simple rakha: har message ek line, JSON format mein - kisi bhi language se bhejna easy
  • Ek alag HTTP "control port" (9101) bhi banaya - backend se ulta command bhejne ke liye
  • Pehle terminal mein secret type karna padta tha - baad mein python-dotenv add kiya taaki secret .env file se load ho, kabhi terminal history mein na jaaye

Logic

Do independent direction hain isi file mein: (1) TCP se data aata hai → console par print → backend ko forward. (2) Backend se command aata hai (HTTP) → jis TCP client se connected hai use likh diya jaata hai. Dono ek hi process mein saath-saath chalte hain, ek dusre ko block nahi karte.

strategy-feed/requirements.txt + .env.exampleNaya

Kya hai

requirements.txt mein Python packages ki list (aiohttp - HTTP calls ke liye, python-dotenv - secret load karne ke liye). .env.example ek template hai jo dikhata hai kya-kya config chahiye, real secret ke bina.

Kyun banaya

Har naye Python project ki tarah - dependencies aur config ka ek standard, safe tareeka chahiye tha.

02 — Naye Files: Strategy Feed System (aage)

Backend aur frontend ka hissa

server/src/routes/strategyFeed.routes.jsNaya

Kya hai

2 naye API endpoints: POST /api/strategy-feed/ingest (Python se data andar aata hai) aur POST /api/strategy-feed/command (trader se command bahar jaata hai).

Steps jo follow kiye

  • /ingest: normal login se protect nahi kiya (kyunki yeh Python server se aata hai, kisi insaan se nahi) - iske bajaye ek shared secret header check kiya
  • /command: normal trader login se protect kiya (authenticate + authorize('TRADER')), same pattern jo order-placement mein pehle se use ho raha hai

Logic (ek important detail)

Secret check mein: agar server par secret set hi nahi hai, to request ko reject karna hai, allow nahi. Yeh isliye zaroori hai kyunki agar galti se secret ka env variable set hona bhool jaaye, aur code sirf "header === secret" check kare, to dono undefined ho jaate aur match ho jaata - matlab bina kisi secret ke koi bhi data bhej sakta. Isliye pehle check hai "secret set hai ya nahi", tabhi match dekha jaata hai.

client/src/hooks/useStrategyFeed.jsNaya

Kya hai

Ek React hook jo WebSocket se live updates sunta hai, jab bhi Strategy Panel khula ho.

Steps jo follow kiye

Naya pattern nahi banaya - pehle se ek similar hook tha (useOrderUpdates.js, orders/fills ke liye), usi ka structure copy kiya: ek shared WebSocket connection, jo sirf tab khulti hai jab koi component use kar raha ho, aur band ho jaati hai jab koi nahi.

Logic

Aane wale message ka type field check karta hai - sirf "STRATEGY_FEED_UPDATE" wale messages ko aage bhejta hai, baaki (market ticks, order updates) ignore karta hai. Isse ek hi WebSocket connection kai alag-alag cheezon ke liye reuse ho jaata hai.

Yeh sab ek dusre se connected kaise hain Agla page (Section 03) mein ek diagram hai jo dikhata hai in files ka aapas mein connection, aur purane files mein kya badlav hua isi wajah se.

04 — Baaki 3 Naye Files

Yeh teeno independent tools hain - app ke andar import nahi hote

In teeno ka app ke chalte hue code se koi seedha connection nahi hai - inhe "tools" ki tarah samjho, jo app ke bahar se app ko check/verify/document karte hain.

.github/workflows/ci.ymlNaya

Kya hai

GitHub Actions ka CI/CD pipeline - har push par automatically 2 jobs chalata hai.

Kyun banaya

Pehle koi automatic check nahi tha. Agar galti wala code push ho jaaye, kisi ko pata nahi chalta jab tak manually test na kare.

Steps

  • "client" job: lint check + production build
  • "server" job: ek throwaway Postgres database spin up karta hai (GitHub ke apne feature se), saare migrations run karta hai, phir asli server ko us par boot karke /api/health check karta hai

Logic

Dummy connection string se test nahi kiya - kyunki server startup par hi ek real database query chalti hai (refreshAllRmsCaches). Isliye ek asli, fresh Postgres chahiye tha CI mein bhi, warna test jhoothi confidence deta.

server/scripts/load-test-orders.jsNaya

Kya hai

Ek tool jo order-placement API ko bahut fast, bahut saare requests bhejke test karta hai.

Kyun banaya

NSE ka rule hai max 120 orders/second per trader - lekin kabhi test nahi kiya tha ki asal load mein system kya karta hai.

Steps

  • Disposable (use-and-throw) test trader accounts banata hai
  • Un accounts ke liye seedha JWT token banata hai (login process se guzre bina, taaki test fast chale)
  • Ek saath bahut saare orders bhejta hai, result record karta hai (kitne accept/reject hue, latency kitni thi)
  • Test ke baad apna banaya hua saara data khud delete kar deta hai

Logic - aur ek zaroori baat

Pehle version mein ek badi galti thi - agar kaafi trader accounts already the, to woh unhi ko reuse kar leta tha testing ke liye. Cleanup step phir us account ka SAARA data delete kar deta - test data ke saath-saath real data bhi. Yeh asal mein hua bhi (Section 05 dekho). Fix karne ke baad, ab yeh hamesha naye disposable accounts hi banata hai, aur cleanup se pehle ek hard check karta hai - agar list mein koi bhi account "disposable" na ho, to poora cleanup hi cancel ho jaata hai. Matlab ab yeh galti dobara ho hi nahi sakti.

docs/REDUNDANCY_AND_FAILOVER.mdNaya

Kya hai

Documentation - agar database server hi crash ho jaaye to kya hoga, uski planning.

Kyun banaya

Aapne pucha "database backup aur redundancy kaise fix karein" - backup to already tha, lekin redundancy (zero-downtime failover) bilkul nahi tha.

Logic - kyun sirf documentation, code nahi

Redundancy banane ke do rasta hain: (a) cloud database (jaise AWS RDS) use karo - yeh sirf ek setting/toggle jitna simple hai, (b) khud host karo - iske liye Patroni/repmgr jaisi tooling chahiye, jo kaafi zyada kaam hai. Konsa rasta lena hai, yeh depend karta hai ek decision par jo abhi tak hua hi nahi - deployment kahan hoga. Aapne khud kaha "abhi sirf plan likho, kuch build mat karo" - kyunki galat rasta pehle build karna time waste ho sakta tha.

05 — Ek Zaroori Baat

Ek galti hui thi, isliye poora sach yahan hai

load-test-orders.js banate waqt, uske pehle version ne ek real trader account (Trader1) ko test ke liye reuse kar liya. Test khatam hone ke baad cleanup step ne us account ka SAARA data delete kar diya - jisme 2 asli, real orders bhi the (test data nahi).

Kaise pakda gaya, aur kaise theek kiya

  1. Routine verification ke dauraan ek row count match nahi hua - turant check kiya, assume nahi kiya ki sab theek hai
  2. Confirm hua ki 2 real orders (aur unki fills, history, audit trail) delete ho gaye the
  3. Nightly backup se saare 18 rows wapas restore kiye - bilkul same ID, same timestamp, same values ke saath, verify karke
  4. Tool ko fix kiya - ab yeh sirf disposable accounts banata hai, aur ek hard safety-check hai jo kabhi bhi real account ko touch hone hi nahi deta
Yeh honestly kyun bataya Galti chhupane se koi fayda nahi - aur is incident ne asal mein yeh bhi prove kiya ki backup system genuinely kaam karta hai, sirf theory mein nahi.
